# Feature Specification: GPU Sandbox Pipeline for A/B Testing

**Feature Branch**: `007-gpu-sandbox-pipeline`
**Created**: 2025-12-11
**Status**: Draft
**Input**: User description: "Create sandbox GPU pipeline on Vast.ai for A/B testing YOLO11 detection and classification against existing Gemini pipeline"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Enable Parallel Pipeline Processing (Priority: P1)

As a system administrator, I want to enable GPU-based deer detection to run in parallel with the existing Gemini pipeline so that I can compare detection accuracy between the two approaches without disrupting the current workflow.

**Why this priority**: This is the core functionality that enables A/B testing. Without parallel processing, no comparison data can be collected.

**Independent Test**: Can be fully tested by uploading a batch of trail camera photos and verifying that both pipelines process the same images, with results tagged by their source.

**Acceptance Scenarios**:

1. **Given** a photo batch is uploaded, **When** the GPU pipeline is enabled via configuration, **Then** both Gemini and GPU pipelines process each photo independently and store results with their respective source identifiers.
2. **Given** the GPU pipeline is disabled, **When** a photo batch is uploaded, **Then** only the Gemini pipeline processes the photos (existing behavior unchanged).
3. **Given** both pipelines are running, **When** one pipeline fails, **Then** the other pipeline continues processing unaffected.

---

### User Story 2 - Compare Detection Results by Source (Priority: P2)

As a product owner, I want to filter and view detection results by their analysis source so that I can evaluate which pipeline produces more accurate deer detections.

**Why this priority**: Enables data-driven decision making about which pipeline to use in production. Requires P1 to generate data.

**Independent Test**: Can be tested by querying detections filtered by source and comparing detection counts, bounding box accuracy, and classification results.

**Acceptance Scenarios**:

1. **Given** photos have been processed by both pipelines, **When** I filter detections by source "gemini", **Then** I see only detections generated by the Gemini pipeline.
2. **Given** photos have been processed by both pipelines, **When** I filter detections by source "gpu", **Then** I see only detections generated by the GPU pipeline.
3. **Given** a photo with detections from both sources, **When** I view the photo details, **Then** I can see and compare detections from each source side-by-side.

---

### User Story 3 - Remove Sandbox Infrastructure (Priority: P3)

As a system administrator, I want to cleanly remove all sandbox GPU pipeline code and infrastructure so that once A/B testing is complete, the codebase returns to a production-ready state without lingering experimental code.

**Why this priority**: Critical for maintainability but only needed after testing concludes. All sandbox code must be isolated for easy removal.

**Independent Test**: Can be tested by following removal instructions and verifying no GPU pipeline artifacts remain while existing functionality continues working.

**Acceptance Scenarios**:

1. **Given** the sandbox pipeline exists, **When** I follow the documented removal steps, **Then** all GPU-specific code and configuration are removed without affecting Gemini pipeline functionality.
2. **Given** the sandbox has been removed, **When** I process new photos, **Then** only the Gemini pipeline processes them with no errors referencing removed GPU components.

---

### Edge Cases

- What happens when the GPU worker is unreachable during batch processing? (System logs error and continues with Gemini-only processing)
- How does the system handle GPU worker timeout during image processing? (Retry with configurable limit, then fail gracefully)
- What happens if the GPU worker returns invalid/malformed detection data? (Validate response schema, discard invalid results, log error)
- How are partial batch failures handled? (Process what's possible, report failures per image)

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: System MUST process photos through both Gemini and GPU pipelines when GPU pipeline is enabled
- **FR-002**: System MUST tag all detection results with their analysis source identifier ("gemini" or "gpu")
- **FR-003**: System MUST allow filtering detections by analysis source
- **FR-004**: System MUST control GPU pipeline activation via environment configuration
- **FR-005**: GPU pipeline MUST detect deer in images and output bounding box coordinates
- **FR-006**: GPU pipeline MUST classify detected deer by sex (buck/doe), age class, and antler characteristics
- **FR-007**: GPU pipeline MUST accept batched image processing requests
- **FR-008**: System MUST maintain existing Gemini pipeline behavior when GPU pipeline is disabled
- **FR-009**: All GPU-specific code MUST be isolated in dedicated directories/files for clean removal
- **FR-010**: System MUST handle GPU worker failures without affecting Gemini pipeline processing

### Key Entities

- **Detection**: Represents a detected deer in an image. Extended with `analysis_source` to track which pipeline generated it ("gemini" or "gpu").
- **GPU Worker**: External service that receives image batches, performs detection and classification, and returns structured results.
- **Analysis Source**: Enumeration indicating which pipeline generated a detection result.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Both pipelines successfully process the same batch of 100+ photos with results stored for comparison
- **SC-002**: Detection results can be filtered and compared by source within the existing UI
- **SC-003**: System processes photo batches with GPU pipeline enabled without increasing Gemini pipeline processing time
- **SC-004**: GPU worker processes batches of 10 images in under 30 seconds (excluding network transfer)
- **SC-005**: Sandbox removal can be completed in under 30 minutes following documented steps
- **SC-006**: After sandbox removal, all existing tests pass and Gemini pipeline functions normally

## Setup Requirements

### Vast.ai Account Setup
- Create account at console.vast.ai
- Add credits (minimum $5 to start; pay-by-the-second billing)
- Generate API key: Account → API Keys in Vast.ai console

### Environment Configuration
The following environment variables must be configured in `.env.local`:

| Variable | Required | Description |
|----------|----------|-------------|
| `GPU_PIPELINE_ENABLED` | Yes | Set to `true` to enable parallel GPU processing |
| `GPU_WORKER_URL` | Yes | HTTPS URL of the Vast.ai instance (e.g., `https://xxx.vast.ai:8000`) |
| `VAST_API_KEY` | No | Optional: for future automation of instance management |

### GPU Instance Requirements

| Resource | Minimum | Recommended |
|----------|---------|-------------|
| GPU | RTX 3090 | RTX 4090 / RTX 5090 |
| VRAM | 16GB | 24GB |
| System RAM | 32GB | 64GB |
| Disk Space | 50GB | 100GB |
| Reliability Score | 95%+ | 99%+ |

Vast.ai search filter: `"gpu_name=RTX_4090 gpu_ram>=24 cpu_ram>=32 reliability2>=95"`

### Network Requirements
- GPU worker exposes FastAPI server on port 8000
- Vast.ai uses Cloudflare tunnels for secure HTTPS access
- TineSight backend must be able to reach the GPU worker URL

### Estimated Costs (Sandbox Testing)
- RTX 4090 pricing: ~$0.30-0.50/hour
- Initial testing budget: ~$15-20 total
- Production estimate: varies by usage volume

## Assumptions

- Vast.ai GPU instances with CUDA support are available and accessible from the TineSight backend
- YOLO11x model weights and EfficientNetV2 classifier weights are publicly available or can be included in the worker image
- The existing Trigger.dev infrastructure supports triggering parallel jobs for the same batch
- Network latency between TineSight backend and Vast.ai instances is acceptable for batch processing
- Classification models will use pretrained weights initially; fine-tuning on deer data is a future optimization
- The GPU worker will be deployed manually on Vast.ai for sandbox testing (not automated provisioning)

## Scope Boundaries

### In Scope (Phase 1)
- YOLO11x deer detection with bounding boxes
- EfficientNetV2 classification for sex, age class, and antler characteristics
- Parallel processing with existing Gemini pipeline
- Source tracking for A/B comparison
- Feature flag configuration
- Clean removal path

### Out of Scope (Phase 2 / Future)
- Embedding generation (DINOv2 or MegaDescriptor)
- Re-identification matching using GPU-generated embeddings
- Automated Vast.ai instance provisioning
- UI components specific to GPU pipeline metrics
- Fine-tuning classification models on deer-specific data
