# Upload audit — 2026-09-05

Read-only application review. No production access/writes and no application changes. Paths below are relative to /home/clachance14/projects/TineSight. Both Bulk Upload and Simple Upload are mounted product flows. lib/upload/uploader.ts is NOT used by either mounted flow.

Historical context supplied by parent: another Claude session observed Drew July 26 with 849 stored photos, all processing completed and variants ready, versus 854 attempted over 18 batches; July 31 session uploading with zero batches/images. The lead auditor subsequently verified those session/photo states with read-only database queries on September 5; the detailed review below itself used no production access. Findings below are reproducible code defects or static causal paths, NOT a claim to have proved Drew's particular cause. EXIF failure precedes session creation in Bulk Upload, so cannot by itself explain a NEW empty session already created. A zero-batch session is more consistent with session creation succeeding followed by initialization failure. Fully processed/variant-ready historical photos point away from a still-running ingest pipeline.

## Prioritized findings

1. **P1 — Completion handoff failures are silently treated as upload success.** components/upload/BulkUploader.tsx:617 and app/(dashboard)/upload/page.tsx:359 await fetch('/api/photos/upload/complete') without inspecting response.ok. A 500 when Trigger.dev is unavailable (route explicitly reverts batch to pending), 401 from expired auth, or 400 results in all transfer rows marked completed and BulkUploader:725 showing complete, while DB photos remain pending forever. Retrying blobs isn't enough: the missing operation is durable enqueue. Check the response, retain per-batch handoff state, retry idempotently, and display recoverable processing-start failure. Simple path also lacks outer try/finally: network rejection at this fetch can leave global state uncleared.

2. **P1 — Processing starts before failed storage transfers are retried, and includes missing objects.** BulkUploader:614-621 dispatches after initial attempts; retries only start at :661 and may be delayed behind many remaining batches. Simple path :359 / :417 has the same ordering. app/api/photos/upload/complete/route.ts:82-96 ignores uploadedImageIds and takes ALL pre-created pending image rows; :114 calls their count authoritative although they do not prove upload success. analyze-photo and variant jobs can exhaust retries downloading nonexistent originals before client retry eventually uploads them; no new enqueue follows a successful client retry. Defer each failed file's handoff until storage success, persist independent transfer readiness, and reconcile intended/accepted/uploaded/failed counts separately. Existing total_images adjustment protects against failed URL generation but not failed blob transfers.

3. **P1 — Failed batch initialization disappears instead of failing files.** BulkUploader:632-635, :645-648 and :654-656 catch every init failure, return null, and filter the batch away. No affected file becomes failed and no retry happens; :725 still sets complete. Global isUploading can remain true because those files remain pending (lib/stores/upload.ts:240-246). Simple page:384-388, :399-403 mirrors this. Trigger with one >50 MB accepted file, a temporary init 500, or blank browser MIME type. Both uploaders accept extension-only files, but BulkUploader:557 / simple page:284 use ?? for file.type, forwarding empty string; API rejects the entire chunk. Reject invalid files individually before session creation, normalize extension MIME, retry initialization, and mark every unrecoverable chunk member failed. Track empty-session failure explicitly.

4. **P1 — Resume dedup skips files whose objects never uploaded.** app/api/photos/check-duplicates/route.ts:106-110 queries image rows by size without a storage-readiness predicate. /upload creates these rows before any transfer. Refresh/close after signed URLs are generated, then reselect the folder: all reserved rows match filename+size, so BulkUploader:493-494 skips missing objects. This defeats the advertised interrupted-upload recovery and leaves phantom pending photos. Persist upload_status/completed_at after verified storage success; resume incomplete reservations instead of deduplicating them.

5. **P1 — Worker load/runtime failure permanently stalls EXIF extraction.** lib/upload/ExifWorkerPool.ts:111-115 only logs onerror and never resolves/rejects pending tasks; extractExif has no timeout. BulkUploader:435 awaits sequentially and cannot reach its catch/fallback. Trigger by worker script load failure/CSP/module error. Reproduced with the real class transpiled in memory and a mocked worker; error left pendingTasks=1 and promise unsettled. Track tasks per worker, reject/recreate on error, and enforce a deadline with metadata-free fallback. This happens BEFORE session creation in Bulk Upload.

6. **P1 security — Foreign session UUID accepted for linking own batch, permitting cross-account session corruption.** app/api/photos/upload/route.ts:197-198 passes caller-provided uploadSessionId without ownership verification; lib/services/batches.ts:243-246 only updates owned batch id. FK checks existence, not tenant equality. Migration 025:90-126 SECURITY DEFINER trigger then recalculates the referenced session regardless of its owner. Processing_batches RLS checks the batch's own user_id only; migration 048 changes trigger search_path/execute permissions but does not add same-owner validation. A signed-in caller who knows another session UUID can attach own batches and change victim totals/status. Add API ownership check plus DB constraint/trigger enforcing batch.user_id=session.user_id, including direct PostgREST writes. This was verified statically, not exploited against production.

7. **P1 — Distinct same-basename photos can be skipped or share a storage object.** BulkUploader:493-494 filters by filename alone even though API matches filename+size. If imported folder contains A/IMG001.JPG size 100 and B/IMG001.JPG size 200 and size 100 exists, BOTH are dropped. Separately lib/services/photos.ts:1222 builds user/batch/filename, so two new same-name files in the same chunk receive the same object path even when contents differ; storage upload conflict or two rows referencing one photo results. Folder upload explicitly recurses directories. Return per-input IDs or filename+size keys for dedup and generate storage paths using image/file UUID, preserving original_filename independently. Real content hashing is needed to distinguish same-name same-size photos reliably.

8. **P1/P2 — Analysis retries count one photo more than once and can prematurely complete batch/session.** trigger/jobs/analyze-photo.ts:833-851 increments processed+failed in catch then rethrows for configured three task attempts; success also increments processed+successful at :749-755. A single failing image can count three times; migration 016:9 auto-completes at processed_images>=total_images. A transient failure followed by success inflates failure+processed totals and can hide other unprocessed work; handoff retries/fanout partial failures can create further duplicates because batch-process.ts does not assign idempotency keys. Use terminal-status transitions and exactly-once counters per photo; count failure only after retries exhausted. DB counter errors are merely logged (:758-764), another permanent pending-batch risk even when images succeeded.

9. **P2 — Simple Upload decodes full originals solely to throw away the preview.** components/photos/photo-uploader.tsx:110-161 FileReader.readAsDataURL -> Image -> canvas; :240 awaits it for every file but returns void and never uses thumbnail. Promise.all at :224 drives adaptive batches (EXIF maxChunkSize 500 in lib/throttle/constants.ts:99). Full-resolution decodes plus base64 buffers needlessly exhaust browser memory/CPU, especially phone Safari; the image variants ADR explicitly documents this failure class. Remove unused thumbnail generation from upload preparation. EXIF extraction can use bounded slices/workers. This is a concrete unnecessary decode path, but crash threshold wasn't device-tested.

10. **P2 — The advertised upload concurrency cap is applied to chunks, not files.** BulkUploader:589-614 / simple page:319-352 creates an XHR for every member, then parallelChunks such chunks run simultaneously. Current config permits chunkSize=50 and parallelChunks=6 => up to 300 active/queued XHRs, ignoring UPLOAD_CONFIG.PARALLEL_UPLOADS=5 and the dormant UploadManager limiter. Values captured once before pipeline, so AIMD updates don't reduce this run's fanout. Network latency/timeouts amplified for SD-card workloads. Put a single shared file semaphore around XHR transfers and use it across chunks and retries.

11. **P2 — Navigation/tab switch doesn't cancel async upload work.** BulkUploader:129 calls AbortController.abort but its signal is never passed to fetch or wired to XHR, nor checked in loops. Unmount during extraction terminates the pool, but per-file catches treat termination as harmless missing EXIF and continue every remaining file, then begin upload from an unmounted component. Tabs remain switchable (upload/page.tsx:570-581), so switching to Simple during extraction can cause background uploads/new global-store mutations and duplicate work. Either move upload ownership outside tab/page lifetime with intentional persistence or implement one cancellation signal across loops/fetch/XHR and treat cancellation distinctly from metadata failure.

12. **P2 — Cancellation is not durable against jobs/batches arriving after the request.** lib/services/upload-sessions.ts:~350 updates ONLY currently processing batches, then marks current image rows. Pending batches have no cancelled_at. batch-process.ts unconditionally sets status processing and does not consult session cancellation. In-flight browser initialization/upload is unaffected (finding 11), so later linked batches can process normally; migration025 aggregation ignores cancelled session state and may overwrite it with processing/uploading. Set session cancellation atomically first, block new batch linkage/enqueue and job starts for cancelled parents, and propagate browser cancellation. Existing analyze-photo cancellation guard does correctly skip jobs whose BATCH cancelled_at was set before job start; it does not cover pending/new batches.

Additional observations, lower priority: check-duplicates endpoint doesn't page size-matching rows, so >1000 matching DB rows silently omit real duplicates; UploadManager.abort calls pLimit.clearQueue leaving queued batch promises unresolved, but this manager is not on live upload UI path; missing/malformed contentType causes .toLowerCase exception/500 rather than structured 400; API completion accepts unbounded batches though mounted clients cap at 50, so pendingImages can truncate at 1000 for direct large requests; camera assignment uses first file metadata for an entire chunk (upload route:206-235) despite bulk recursive mixed-camera folders. Active-session hook initializes sessionStorage once on mount and never reacts to setter, and can stop polling while session has zero/currently-no-pending photos before future chunks exist; see lib/hooks/use-active-batch.ts:42-68, :101-108, :130-137, :170. Parent may consolidate with UI agent.
