# Filtering and sorting intent versus current active UI

Scope: Repository planning artifacts and active code only, not a claim to have read inaccessible conversation history. Read specs/004-photo-confidence-filter/spec.md and plan.md, specs/005-gemini-deer-pipeline/spec.md, specs/002-photo-pipeline/spec.md, product vision, mobile hardening charter, ADR0004, and active/legacy filter controls. No app edits.

## What was already intended

- **Many cameras, frequent high-volume pulls, reduce noise.** `.specify/memory/product-vision.md:7-9` explicitly says 10–20+ cameras, thousands per month, 80%+ empty/blurry/non-deer; :22-24 says hours sorting is core pain. `specs/002-photo-pipeline/spec.md:16-18` and :48-59 define bulk imports → automatic triage → Has Deer versus Empty/Other with manual correction. This is existing product intent, not an audit invention.
- **An adjustable quality/noise filter.** `specs/004-photo-confidence-filter/spec.md:26-28` calls for ANY matching detection, a threshold slider, immediate update. :42-44 originally calls for Has Deer=true/minConfidence=50% defaults and filtered count. :74-76 requires threshold-preserving on/off toggle. :90-100 calls for removable chips and useful no-results explanation. :108-119 lists functional requirements; :136 requires navigation persistence and exact shared link restoration. `specs/004-photo-confidence-filter/plan.md:18-19` targets <1 second filter updates at 10,000+ photos. These are historical explicit requirements; the precise original default must be reconciled with later score/tier decisions below.
- **Triage, not merely an image gallery.** `specs/005-gemini-deer-pipeline/spec.md:34-48` requires batch summary with bucks/does/unknown/empty, 10+ points filter, drilling into detections, bulk Archive Empty Photos hidden from normal views. :160-162 explicitly requires point ranges, sex and bulk archive. :185 targets 10+ bucks in two clicks. `specs/002-photo-pipeline/spec.md:138-147` requires failed-processing filter and retry.
- **Later intent refines old triage semantics.** `docs/adr/0004-trophy-gated-ai-cost-cascade.md:73-77` explicitly specifies score-based photo tiers (trophy → other buck → doe → non-deer → empty), lower tiers collapsed not destroyed, separate people/vehicle security surface never automatically hidden. This means old spec005's broad has_deer=false = empty is no longer a safe direct implementation of current intent: it conflates blank frames, hogs and people. `docs/plans/2026-06-20-mobile-core-hardening.md:34-36` keeps imports/processing on desktop and mobile browsing/filtering/review/sharing. :91-93 contains that hardening project's preserve-photos constraint; do not turn it into an invented universal ban on user-requested manual deletion.

## What the live gallery currently exposes

`app/(dashboard)/photos/page.tsx:155-176` mounts PhotoQuickFilters and PhotoGrid only. URL parser at :25-57 supports sex, minScore, areaNames, named deer, dateFrom/dateTo, otherAnimals, and three sort fields/direction. It ignores old cameraId/uploadSessionId/status/hasDetections/minConfidence/point-range/isArchived shared-link values.

`components/photos/photo-quick-filters.tsx:33-38` exposes Highest score, Newest captured, Oldest captured, Recently uploaded. :127 onward exposes All/Bucks/Score; `components/photos/photo-more-filters-sheet.tsx:101-167` exposes Area, Named buck, Date, Other animals. This is a useful focused surface but excludes whole operator workflows rather than simply hiding advanced controls behind disclosure.

Current source dimensions must be kept distinct: camera identifies device, location identifies deployment place, area is grouping/location text, and upload session identifies import event. Current area query uses processing_batches.area_name (`lib/services/photos.ts:93-160`), not images.location_id; relocation service updates images.location_id (`lib/services/photos.ts:1432-1462`). Do not promise they are interchangeable without a domain/data decision.

## New proposals, clearly distinguished from existing requirements

These are audit recommendations for reconciling the documented workflows, not claims that the user previously specified exact labels/layout:

1. Offer saved review views with combinable **source** (camera, location/area, upload event), **content** (bucks, does, other animals, people/vehicles, genuinely empty), **AI/review state** (processing/failed/needs review/quality), and **time/score**. Progressive disclosure can keep primary controls compact without removing power-user capability.
2. After an import, land in **that upload session**, show counts/progress/retry, default its ordering to upload/file order or capture order by deliberate choice. Keep capture time versus upload time explicitly labeled; Drew's 2020 camera timestamps should not be silently rewritten to solve sorting visibility.
3. Add reviewable, reversible **archive/trash workflow** with exact matching count and restore if the user wants trash semantics. Existing archive is evidence for hiding; retention period, automatic deletion, new default filters, and trash naming are new decisions, not previously authorized requirements. Preserve people/vehicle visibility and uncertain frames until explicitly classified/reviewed.
4. Restore existing source/preset/selection capabilities through the current design system only after predicate parity, cursor pagination, dates, errors and full-result bulk IDs are verified. One canonical filter schema should drive URL → grid → detail → counts → bulk actions.
5. Update old spec defaults explicitly: score/tier-based prioritization versus all photos/newest capture versus old 50%-confidence deer default are conflicting historical states. User's present desired workflow should decide; audit should not silently choose the oldest or newest artifact as mandatory product behavior.
