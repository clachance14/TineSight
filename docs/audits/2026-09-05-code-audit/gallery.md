# Photo sorting / gallery audit — original findings

Historical baseline recorded before authorized implementation. Findings below describe the original defects, not the current working tree; see [gallery implementation evidence](gallery-implementation.md).

The initial pass was a read-only application audit. Read CONTEXT.md, CLAUDE.md, ADRs 0003 and 0004; traced active gallery, API list/ids, photo service, detail navigation, date controls, infinite query, realtime. No application files modified. Current app default is captured_at DESC; don't characterize old camera dates as a bug in itself (Drew's camera dates 2020 can correctly sort far below 2026 captures). Existing working-tree changes were landing-page work only.

## Prioritized concrete findings

1. **P1 — Pagination cursor is completely ignored; photos after first 50 are inaccessible.** `lib/services/photos.ts:621-624` and `:686-689` use offset/range only; neither getPhotos branch reads filters.cursor. `app/api/photos/route.ts:438-458` creates nextCursor and route fixes offset=0; `lib/hooks/use-photos.ts:340-341` sends cursor. Every next page is identical to first, for both plain and detection-filtered requests, with duplicate thumbnails and repeated nextCursor. Executable in-memory harness using ACTUAL transpiled getPhotos and installed Supabase query builder with custom fetch confirmed identical URLs for page 1 and page 2 (capture-date query and score+buck query). No network/database calls.

2. **P1 — Opening a photo discards active filter and sort context.** `app/(dashboard)/photos/page.tsx:173-175` pushes only `/photos/${id}` despite URL-based filters. Select named buck/area/score/date, open tile, swipe: detail receives no query, browses whole account; its Back to Photos loses filters too. `lib/photos/detail-filters.ts` supports many values but can't recover discarded values. Pass normalized query including defaults.

3. **P1/P2 — Viewer order disagrees with gallery.** `lib/services/photos.ts:973-1006`: adjacent lookup fetches only imported_at and hardcodes imported_at DESC/id DESC. Gallery defaults captured_at DESC (`app/(dashboard)/photos/page.tsx:17`) and offers Highest score and Oldest. Even correcting #2 will leave swipes out of order/reversed. Example capture order A,B,C; upload order C,A,B: opening B and Next fails to reach C. Need same order/null policy and tuple comparator as list query.

4. **P2 — Infinite gallery stalls around 550 and discards earlier photos even after cursor repair.** `lib/hooks/use-photos.ts:356` maxPages=10 evicts first page at page 11, so flattened photo count stays 500. `components/photos/photo-grid.tsx:262-273` latches next-page requests only on photos.length. Once it requests while length=500, new response still length=500, no subsequent request can run. No getPreviousPageParam/fetchPreviousPage path can restore evicted first 50. Also any failed next-page request leaves same-length latch locked with no retry control; changing filters can hit stale equal-length latch. Need compatible cache window + virtualizer anchoring or uncapped lightweight metadata with bounded image DOM.

5. **P2 — Today/date upper boundary excludes the selected day's photos.** `components/photos/photo-date-range-picker.tsx:55-60` sends same YYYY-MM-DD for Today from/to. `lib/services/photos.ts:388-392` directly applies captured_at >= dateFrom AND <= dateTo, i.e. single midnight instant. Last7/Last30 omit all of today after midnight; custom last day likewise omitted. Picker generates local dates but database timestamp comparison receives no local offset. Use local-day inclusive start/exclusive next-day end converted to instants; preserve capture-date semantics.

6. **P2 — Custom date filter cannot open; selected preset is wrong.** `components/photos/photo-more-filters-sheet.tsx:137-147` passes dates but neither datePreset nor preserves callback datePreset. Picker defaults to last30days at `photo-date-range-picker.tsx:24`; custom fields are rendered only for datePreset==='custom' at :151. Clicking Custom changes nothing; clicking Today leaves Last30 selected. Parent must persist/derive preset state.

7. **P2 — Gallery hides request failures as no photos or stale results.** Active page destructures no query.error (`page.tsx:98-104`) and PhotoGrid external-data branch forces error:null (`photo-grid.tsx:161-166`). Actual API timeout/500 eventually shows 'No photos yet' on initial load, or prior filter data from keepPreviousData. Built-in error rendering is unreachable through actual page. Pass errors/refetch through externalData; distinguish filtered-empty from import-empty.

8. **P2 — Thumbnail generation and score completion can remain invisible.** `lib/hooks/use-photos.ts:361-377` polls only while loaded photos detection_status pending/processing; variants run independently per ADR 0003. Once analysis completes, variant_status pending/processing no longer keeps gallery polling. Gallery doesn't mount useRealtimePhotos (only BulkUploader does). Pending preview may stay Preparing after variant ready, and score-filtered results can stay empty while newly completed jobs should enter set, until stale-time/focus/refetch. Need polling tied to actual background stages/account upload activity or correct invalidation/realtime.

9. **P2 — Bulk ID endpoint ignores legacy single-area filter when combined with detection filters.** `lib/services/photos.ts:739-759`: hasOtherImageFilters omits areaName, and early return sends global matching detection ids before resolveBatchIdFilters. getPhotos honors areaName. Actual service harness getPhotoIds(user,{sex:'buck',areaName:'North'}) issued ONLY RPC, no processing_batches/area query, proving broader selection. Bulk UI component currently appears unmounted from active gallery, so latent API/backlog risk (do not claim current visible delete flow). batchId likewise appears never applied anywhere in shared photo filters, though API accepts it.

10. **P2 / performance — Grid starts an unnecessary second unfiltered query.** `components/photos/photo-grid.tsx:156` always invokes usePhotosInfinite(externalData ? undefined : filters) with no enabled=false option. Active page already calls usePhotosInfinite(filters), so every gallery mount fires separate unfiltered 50-photo query, signs variant URLs and may poll unused data. On large dogfood accounts this wastes DB/URL latency and background requests during filtered browsing.

11. **P2 / ADR constraint — Detail fallback loads originals when variants absent.** `lib/services/photo-view.ts:69` uses mediumResult.data ?? fullResUrl for regular imageUrl; PhotoDetailClient renders that image and pager prefetches neighbor views. Violates ADR 0003's variant-only normal viewing and can decode multiple camera originals during missing-variant uploads. This differs from explicit zoom/download where original is intended.

## Executed proof
Actual service transpiled in memory with TypeScript transpileModule; actual installed @supabase/supabase-js; custom fetch returns fake records and records URLs, so no external reads or writes.

- Plain first/next query both: `https://audit.invalid/rest/v1/images?select=*&user_id=eq.user&order=captured_at.desc.nullslast,id.desc&offset=0&limit=51`
- Buck+score first/next both: `https://audit.invalid/rest/v1/images?select=*,detections!inner(id)&user_id=eq.user&detections.deleted_at=is.null&detections.sex=eq.buck&order=best_score.desc.nullslast,id.desc&offset=0&limit=51`
- Select-all buck+area: ONLY `/rest/v1/rpc/get_filtered_detection_images`, whose args never contain an area filter.

No browser smoke or live-account assertions performed by this agent. Evidence above is code-level plus executable service/query proof, not a claim of observed production sessions. Prioritize cursor, preserving context, matching pager order, date controls, then cache window/error/recovery before broad cosmetic redesign.
